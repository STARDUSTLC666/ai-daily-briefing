# AI 日报内容采集与证据链规范

本项目的目标不是把 RSS 摘要直接念成视频，而是生产一档可长期自动化运行的中文 AI 视频早报。

## 核心原则

RSS、Google News、媒体快讯和社区帖子只负责发现线索，不能直接决定最终稿件的信息量。

早报不固定条数，也不做中午档分流。只要是合格、有信息量、证据链足够的 AI 新闻，都可以进入早报；低质、跑题、证据不足的条目进入剔除/待复核池。

主流 AI 模型和产品要最高优先级处理，包括 OpenAI、Anthropic/Claude、Google/Gemini、Qwen、DeepSeek、Kimi、豆包/ByteDance、腾讯混元、智谱 GLM、MiniMax、Mistral、Meta/Llama、xAI/Grok、Hugging Face、ModelScope、NVIDIA、GitHub/Copilot、Ollama、vLLM 等。

每条主视频新闻必须尽量回答：

1. 发生了什么。
2. 具体更新了什么，或证据里出现了哪些关键事实。
3. 对中文观众、普通用户、开发者或 AI 从业者意味着什么。
4. 证据确认到哪一步。

卡片可以短，但必须是短句高信息密度；禁止把有效信息压成“参数、入口、价格未公开”“入口待确认”这类空泛句。

## 标准采集流程

1. **发现线索**
   - RSS / Atom
   - Google News
   - GitHub Release / Changelog
   - Hugging Face / ModelScope 模型更新
   - 国内外 AI 媒体
   - 社区性能反馈、榜单、用户实测
   - X 官方人员一线动态与社区风向（只作分级线索）
   - 每日 07:00 只运行 `sources.yaml` 中启用的快车道，目标不超过 40 个源；关闭项仍可在专项深挖时临时启用，不能为了“源多”让重复镜像和全量论文流拖慢每日成片。

2. **进入原文**
   - 先对已具备网页抓取资格的线索按“事件簇 + 证据等级 + 新鲜度 + 来源多样性”规划 URL 抓取额度；它只优化爬取成本，绝不代替最终新闻选择。
   - 每日自动任务最多富化 32 个候选 URL。合格新闻条数仍不设上限；这里限制的是昂贵的候选正文抓取，不是限制最终新闻数量。
   - 周报、融资、课程、会议、未来日期、无效链接及同域/高频源超额条目不能占用正文抓取额度。
   - 抓取原文标题、正文、发布时间、作者/发布机构。
   - 不满足正文信息量时，不能只用 RSS 摘要生成稿件。
   - 对媒体快讯，要尽量进入原始媒体页或新闻详情页。
   - RSS 的 `pubDate`、站点地图 `lastmod` 和 Google News 聚合时间只表示线索何时浮现。正文存在可靠 `datePublished` 时，以正文首次发布时间判定新鲜度；正文时间比聚合时间早 12 小时以上时，必须保留两者并用正文时间纠正，禁止把旧文章重浮现当成当日新闻。
   - 页面同时出现多份发布时间元数据时，汇总 JSON-LD `datePublished` 与发布类 meta，并取可解释的最早发布时间，避免任一位置的 SSR 当前时间覆盖真正文章时间；`dateModified` 不作为首发时间。
   - X 原帖以精确 `status/<id>` 为证据，发布时间从 status snowflake 或原帖页面核对；账号主页、搜索时间和媒体转述时间不能代替原帖时间。
   - 默认使用 Crawl4AI 进行浏览器级抓取，提取正文 Markdown、图片、链接、元数据和页面截图。
   - 生产定时任务不擅自修改 Python/浏览器环境；Crawl4AI 或 Chromium 失败时退回普通 HTTP 并在 manifest/fact-check 中记录。需要修复运行时只能显式开启 `content_enrichment_auto_runtime_repair`。

3. **寻找官方源**
   - 官网新闻 / 官方博客 / 官方研究页。
   - API 文档、产品文档、价格页、模型页。
   - GitHub Release、Hugging Face、ModelScope 官方组织页。
   - GitHub 预发布版本既要保留 Release/tag 页面，也要检查同仓 compare URL。由 GitHub API 得到的 commit 摘要只有在 compare URL 回写到证据合同时才可进入口播；alpha、beta、rc 必须明确标注为预发布版本。
   - 官方公众号、微博、X、开发者论坛、云产品公告。

4. **同主题合并**
   - 同一模型、产品或事件的多篇报道必须合并成一条新闻。
   - 不要把媒体报道、官方页、评测文章拆成重复新闻。
   - 合并后优先保留事实：能力变化、入口、价格、API、产品接入、参数、榜单、修复项、版本差异。
   - 媒体标题省略产品名或使用标题党时，从正文中识别重复出现的版本化名称（例如 `Riemann-1.0`）作为事件锚点，并改写为事实标题；名称、数字和评测结论仍须逐条绑定正文摘录。

5. **生成稿件与卡片**
   - 新闻稿负责解释。
   - 卡片负责展示信息。
   - 两者不能逐字重复。
   - 高价值新闻可以更长，低价值新闻一句带过。
   - 有明确发布主体、执行周期和具体任务的“人工智能+”行动方案、指导意见或监管规则，可作为黄色政策短讯进入主视频；只写口号、没有时间范围或没有任务内容的政策稿不收录，也不与模型/产品发布混为同类新闻。

## 官方源打不开时的处理

官方源优先，但官方网页打不开时不能直接放弃，也不能硬编。

### 1. 多方式访问官方

依次尝试：

- 普通 HTTP 请求。
- 更换 User-Agent、Accept-Language、Referer。
- 跟随跳转。
- 浏览器渲染后抽取正文。
- 如果页面是前端应用，解析 JS、接口、JSON、静态资源。
- 记录状态码、最终 URL、超时、JS 空白页、403、404 等失败原因。

### 2. 官方等价源兜底

如果官方页面打不开，继续寻找官方等价源：

- 官方新闻稿的转载页。
- 官方公众号/微博/X。
- 腾讯云、阿里云、OpenAI Docs 等产品/API 文档。
- GitHub Release。
- Hugging Face / ModelScope 官方组织页。
- 产品入口页、价格页、模型卡、开发者文档。

### 3. 媒体交叉验证

如果官方源仍不可访问：

- 至少使用两个可靠媒体源交叉验证。
- 只写多源共同确认的事实。
- 单家媒体独有的夸张判断、性能结论或预测，不能写成确定事实。

### 4. 证据等级

内部证据状态建议分为：

- `official_confirmed`：官方源可访问并确认。
- `official_blocked`：官方源存在，但当前不可访问或渲染失败。
- `official_equivalent`：官方等价源确认，例如 GitHub、模型页、文档、云公告。
- `media_cross_checked`：多家可靠媒体交叉确认。
- `single_media_only`：单媒体线索，只能保守进入候选。
- `community_only`：社区线索，主视频慎用，必须有截图或进一步补证。
- `official_personnel_signal`：官方人员在 X 的一线动态；不是正式公告，必须截到原帖。
- `community_rumour`：社区/X 传闻或风向；必须有原帖截图、明确产品/版本和具体观察，最多作为单独的一条短讯。
- `unverified`：证据不足，不进主视频。

## 自动修复与兜底原则

整条流水线默认遵守：

1. 先走产品级工具。
2. 生产环境优先安全兜底；只有显式允许时才自动修复运行时。
3. 兜底仍失败时，记录原因并跳过该条或降级该环节，不能让整期早报无声失败。

具体策略：

- 正文/图片/截图：Crawl4AI → requests 兜底；只有显式开启运行时修复时，才尝试修复 crawl4ai 与 Playwright Chromium。
- 证据截图：复用 Crawl4AI 截图 → Chrome/Edge headless 截图 → 记录失败。
- 配音：Edge TTS `zh-CN-XiaoxiaoNeural`（`+8%`）→ `zh-CN-XiaoyiNeural`；Windows SAPI 与静音只保留诊断兜底，不能通过自动投稿门禁。
- 渲染：Remotion → npm 依赖修复后重试 Remotion → 浏览器 CSS/ASS/FFmpeg 兜底。
- 发布：B 站上传永远先 dry-run，只有用户明确确认才执行真实上传。

### 无人工审核的发布闸门

自动模式不依赖人工审稿，但必须全部通过以下机器门：

1. 真实来源、发布时间、中文化的具体事实和截图契约。
2. 结构化 claim—evidence 口播契约，且视频、字幕、时间轴、B 站简介一致。
3. 低信息、原始英文、乱码、裸 URL、模板话术会定位到新闻卡；系统自动补选重渲染，无法补足最低条数则停止。
4. `run-state.json` 必须是 `QA_PASSED`，并且与 manifest 的 `run_id` 一致；`render-info.json`、ffprobe 流参数和必需截图文件必须真实存在。
5. 实体标签只允许由真实证据支撑：`论文 / arXiv` 必须有 arXiv source/URL。官方技术博客即使带 benchmark 等词，也不能被公开文案误称论文。

### 5. 文案规则

官方打不开时：

- 禁止说“官方确认”。
- 可以说“多家媒体报道”“官方页面当前未能访问到正文”“官方等价源显示”。
- 不要在每条新闻里反复念“待确认”。证据状态应更多放在 fact-check、内部 manifest 或画面角标。

### 6. 截图规则

- 官方可访问：优先截官方页。
- 官方打不开：保存失败原因，并截可用的官方等价源或可靠媒体源。
- 对社区性能反馈、榜单、用户实测，必须保留源头截图。
- X 官方人员动态必须在画面、口播和时间轴标注“**一线消息，未获官方公告确认**”；不得把方向性发言改写成已发布、已上线或已开放。
- X/社区传闻必须在画面、口播和时间轴标注“**传闻/风向，未获官方公告确认**”；单家媒体转述不能抹去该标签，仍须保留原帖截图。原帖抓不到、只剩英文原文、没有具体事实或无法中文化时自动剔除。
- 后续官方恢复访问时，应允许补抓并更新证据。

## 腾讯混元 HY3 这类新闻的要求

如果出现 `HY3`、`腾讯混元`、`Hunyuan` 等主流模型关键词：

- 不能只写“正式发布”。
- 必须尝试抓官方页、产品入口、腾讯云/API、媒体原文、评测文章。
- 需要抽取并合并：Agent 能力、元宝/CodeBuddy/WorkBuddy 等产品接入、腾讯云 TokenHub/API、价格或免费开放信息、能力变化、评测或榜单信息。
- 如果官方页面是前端应用且 HTML 无正文，应继续解析前端资源或用浏览器渲染抽取，而不是把新闻写少。
